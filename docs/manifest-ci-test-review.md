# Manifest CI and test review

Reviewed 2026-10-30 for PR #82 using the private
failure-space-test-design skill.
Scope: manifest admission, canonical indexes, retained releases, installation,
and readiness tests affected by evidence age. This is a focused review, not a
claim that every application test or live provider integration was audited.

## Findings and authority

**Confirmed:** the 30-day value is repository policy, not a JSON Schema rule or
an independently verified provider requirement. Section 9 of
[operational-readiness-v1](../shared/contracts/operational-readiness-v1.md)
introduced it in commit `2371199` on 2026-09-13. Commit `4512af5` implemented
the manifest admission constants on 2026-09-14. The contract specifies maximum
lifetimes of 180 days for instruction evidence, 90 for executable verification,
30 for setup/authentication/provider evidence, and 365 for security reviews.
Provider and credential expiries can impose earlier deadlines.

**Unknown:** the inspected contract and commit history do not explain why
exactly 30 days was selected, quantify its risk tradeoff, or identify an
external requirement. Passing tests can prove implementation of this policy;
they cannot establish that 30 days is the right product or security policy.

**Confirmed defect:** repository validation and canonical index generation
used the current time to reject old manifest evidence. Unchanged bytes could
pass in September and fail in October. Tests exercising archived packages
also mixed fixed fixture dates with the current clock. The failure was a
coupling between static integrity and operational evidence, not schema drift.

**Confirmed defects:** composite status accepted an evaluation time but used
the real clock for nested package admission. Manifest admission also accepted
the exact expiry instant, contrary to the contract's half-open validity
interval: `observed_at <= now < expires_at`.

## Domain and authority map

| Subject | Authority and effect | Confidence |
| --- | --- | --- |
| Package identity and content | Manifest, version, archive digest, lock and receipt; checked before installation commits | Confirmed |
| Canonical index | Derived declaration and digest inventory; generated bytes must be reproducible | Confirmed |
| Current readiness | Exact target, runtime/provider observations, credential generation and evaluation instant; cannot be established by index metadata alone | Confirmed |
| Retained release | Immutable archive and sidecars; elapsed time must not rewrite or corrupt history | Confirmed |
| Catalog view | Derived projection; expired usable-now and capability claims are suppressed while historical observations remain visible | Confirmed |
| Thirty-day policy justification | No independent risk rationale found in inspected sources | Unknown |

Actors include package authors, release publishers, installers, runtime users,
and authentication providers. The protected outcomes are truthful readiness,
intact release history, and preventing stale or substituted authority from
reaching operational use. Installation commits files only after admission;
provider observations remain a separate trust boundary.

## Changes and invariant ledger

| Protected invariant | Enforcement and falsifiable test |
| --- | --- |
| Time alone does not corrupt a package | Structural repository/index checks ignore elapsed evidence age; identical fixtures are evaluated 100 years apart |
| Stale evidence cannot admit operational use | Install/runtime validators still require freshness; fresh versus stale admission and existing remote-admission tests remain active |
| Structural validation still rejects bad metadata | Missing verification remains rejected; a malformed verification timestamp fails both repository and index validation |
| Evidence expires exactly at its deadline | Four scopes tested immediately before, at and after expiry using literal limits from the normative contract |
| Composite evaluation uses one instant | Supplied evaluation time reaches nested provider admission; default time is captured once per composite evaluation |
| Validation does not renew evidence | Fixture bytes are asserted unchanged; registry generation produces no tracked diff; retained releases remain unchanged |

Production package admission defaults to the real clock. There is no CLI or
environment flag to suppress freshness. Eight existing archive/contract tests
use a known admissible package-evaluation instant and restore it with cleanup.
This affects package admission only, not credential, provider, model or smoke
evidence clocks. The test clock seam is process-local and requires serial tests;
tests using it must not use `t.Parallel`.

The canonical registry stores declarations rather than a timeless proof of
readiness. The existing release publisher computes current catalog projections;
installation and runtime checks remain authoritative for operational use.

## Usefulness of the existing tests

| Test family | Assessment |
| --- | --- |
| Schema validation and negative fixtures | Keep. They catch malformed or unsupported contracts; they do not prove execution or provider readiness |
| Canonical schema-definition equality | Keep as a drift check, paired with behavioral valid/invalid fixtures; equality alone is not semantic proof |
| Released archive installation and closure verification | Keep. They catch missing dependencies, digest substitution, selected-version drift and runtime compilation failures. Evaluate historical fixtures at explicit times |
| Receipt, credential-generation and target-isolation tests | Keep. They exercise material authority boundaries beyond happy-path status assertions |
| Freshness and expiry tests | Keep, with controlled clocks and boundary cases. Test the contract, rather than relying on a fixture eventually aging out |
| Repository-wide count/classification assertions | Lower-value and maintenance-heavy. Counts such as 42 skills change with ordinary catalog additions; count alone cannot detect a valid substitution. Prefer explicit approved identity/contract expectations where deletion is material |

The fixed policy number is reasonable to encode as a named contract ceiling,
but should not be scattered as unexplained literals. The readiness producer
also contains 30/90-day literals. A follow-up should centralize versioned policy
defaults and bind evidence to the applicable policy version. Package authors
must not be able to extend their own validity by supplying a larger TTL.

The legacy manifest adapter infers evidence lifetime from execution kind and
authentication status. A single `last_verified_at` cannot represent independent
setup, code-verification and provider observations. Explicit scoped evidence
with `observed_at`, `expires_at`, target identity and policy version is the
better long-term model; that migration is outside this CI repair. Shorter
provider expiry and credential replacement must continue to invalidate earlier.

The adapter's existing five-minute future-clock tolerance is also a policy
assumption. It should be documented and reviewed alongside the stricter
`observed_at <= now` contract rule rather than being treated as a universal
time property. This repair preserves that tolerance.

## Bounded verification and residual risks

The selected failure space crosses static versus operational admission,
fresh/stale evidence, four evidence scopes, expiry boundaries, UTC offsets,
malformed metadata and mixed clocks. It does not attempt arbitrary Cartesian
coverage of all modules, providers or concurrency schedules.

- Expiry boundary coverage: 12/12 selected cases across four scopes.
- Invalid/reference/clock-offset checks: 4/4 selected cases.
- Calendar invariance: the same package at two instants 100 years apart.
- Targeted harmful mutations detected: 4/4, using temporary Go source overlays:
  disabling runtime freshness, accepting equality at expiry, and reintroducing
  wall-clock freshness into structural repository validation, plus ignoring
  the explicit composite evaluation time.
- Complete Go suite, CLI build with the CI test trust root, manifest/schema
  validation, and canonical-index diff gate passed locally.
- Race checks passed across the five affected packages; focused checks also
  cover the final mixed-clock regression and retained-plugin fixture.

These numbers describe only the declared finite space. They are not whole-suite
mutation coverage. No live provider, credential or sandbox verification was
performed, and no verification dates or released artifacts were renewed.

Recommended next work is to document the risk owner and rationale for each
policy ceiling, then consolidate policy handling and migrate the coarse legacy
manifest-age gate to scoped evidence. Review catalog inventory tests separately
from runtime behavior tests. Do not remove expiry checks merely to keep CI
green.
